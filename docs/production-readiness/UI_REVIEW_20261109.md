## Design assessment

The visual system is coherent across the web surfaces: navy/orange branding, clear cards, readable status colors, large primary actions, and mobile layouts that preserve hierarchy. The admin dashboard is the strongest verified interface. Its overview prioritizes waiting trips and rider verification, while service-fee review makes the irreversible action explicit.

The Android flows are structurally ready for device rehearsal, but local builds cannot prove touch behavior, map usability, keyboard avoidance, GPS accuracy, accessibility services, or readability on the two target phones. Those observations must remain open rather than being inferred from Compose source.

The landing page is honest in its current code: release cards say **Coming soon**, both download controls are disabled, and version/checksum data is withheld until verified artifacts exist. Older screenshots showing active-looking hero download links are design evidence only; current automated checks confirm that the actual release controls fail closed.

## Changes completed in this review

- Passenger fare details now state that the rider platform fee is included in the fare and is not an extra passenger charge.
- Rider completion, cash confirmation, history, and earnings use consistent gross/fee/net language.
- Rider service-fee balance and payment history are backed by server data and Realtime refresh, with manual refresh as fallback.
- Admin can configure the official payment destination, inspect balances, and verify or reject submitted references. Pending submissions never clear balances automatically.
- The database records one immutable charge per completed trip and one immutable credit per verified payment; authorization, duplicates, partial payments, rejection, and audit behavior pass 29 focused assertions.
